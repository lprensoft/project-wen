# 上下文的组织

[← 返回 README](../README.md)


一轮请求发出去的上下文分两层：

```
system        [系统环境] + [工具与回复] + [历史与时间] + 各插件的固定提示词 + 你配置的系统提示词   ← 整轮之间一字不变
历史          过往消息；日期翻篇处插一行「（以下是 2026-08-20 星期四 的对话）」，
              隔得久的地方插一行「（此处距上一条消息约 14 小时）」
<本轮状态>    当前时间、距上一条消息、各插件每轮生成的片段（心情/天气/记忆索引…）
本轮输入      你说的话
```

**当前时间不在 system 里，而在历史之后**。这一条同时解决两个问题：

- **模型对「现在」的判断。** 时间放在 system 开头时离生成位置有几千 token 远，而历史对话里出现过的时刻是叙事事实、就在眼前——聊上十几轮之后，模型会把上次那个时刻当成现在，于是在下午继续演深夜。放到历史之后，并明说「与历史里的说法不一致时以这里为准」，才压得住。同理，历史里隔得久的地方会补一行间隔标记：消息的时间戳本来就存着，只是从不发给模型，于是那十几个小时在上下文里根本不存在。
- **提示词缓存。** 缓存都是前缀精确匹配的，system 里放一个每轮都在变的时间戳，等于让整段 system 加历史永远无法命中。DeepSeek 这类服务端自动缓存的提供商没有任何开关可调，唯一的抓手就是前缀别变。

`[工具与回复]` 是给模型的一小段约定：工具结果是它自己那次调用的回执、不是你说的话；一轮只回一次；已经做成的事不重复提交。少了这段，模型调完工具后被要求再生成时会**替你编一句话再回答它**，或者把同一个工具反复提交下去。程序这边还有一道硬护栏：同一轮里同名同参的调用不再执行，同一个工具超过六次不再执行，拦下三次就结束这一轮。

`[历史与时间]` 是另一段约定，针对的是一类很难自己发现的错位。角色某天晚上说「明天给你带两个菜」，那句话此后一直留在上下文里，措辞永远是「明天」。第二天你带走了，但对话里没有任何东西记着这件事已经兑现，也没有任何东西说那个「明天」指的是哪一天——于是当晚它又说了一遍，而它新说的这句「明天」又成了第三天最靠近眼前的证据，自己把自己续了下去。三条约定因此写在一处：正文里的「今天／明天／昨天」按说这话的那条消息所在的**日界线**理解而不是按现在理解；自己说过的打算不代表现在仍然成立、也不代表还没兑现；要判断这类事的状态以 `<本轮状态>` 为准。

日界线就是历史里那行「（以下是 2026-08-20 星期四 的对话）」。只有间隔标记的话，要定位某句「明天」指哪天，模型得把那条消息到末尾的间隔逐段累加——一条它做不可靠的算术链；日界线把它变成一次查表。标注优先前置到你的消息上，角色主动开口的那一轮（心跳发起的轮次里，注入的提示只发一次、后续上下文里就没了）前面没有你的消息可依附，会单独插一行——那类主动说出口的话此前一点时间信号都没有，而「昨天跟我说明天要怎样」多半正是那么说出口的。这些标注只加在发出去的副本上，不落盘，也不影响缓存前缀（它们由消息本来就存着的时间戳推出，生成后再不变化）。

**压缩摘要同样要求写绝对日期。** 摘要是永不裁剪的，它里面的每句话都会以完全相同的措辞出现在此后每一轮的最前面——一条不带日期的「答应了明天带菜」进去，就等于被焊死在那里，每天重新出现一次。压缩器现在收得到日界线，并被要求把相对说法换算成具体日期、未完成的待办写清哪天说的与期限在哪天。

`/status` 会报出最近一轮的缓存命中量，可以据此确认它确实在生效。
